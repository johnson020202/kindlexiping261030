# 越狱与安装

## 先确认设备

在 Kindle 搜索框输入 `;711` 可查看固件信息（部分机型有效）；也可连接电脑读取 `system/version.txt`。本项目当前连接设备记录为：

- 机型：Kindle Paperwhite 3（第 7 代，2015，序列号前缀 `G090KB`）
- 屏幕：1072 × 1448 灰度
- 固件：5.16.2.1.1（PW3 的最终固件）
- CPU：armv7l（i.MX6），**软浮点 armel 用户态**
- 触控：`/dev/input/event1`
- 存储：约 3.3 GB FAT 分区
- 已有 root 脚本入口：搜索框 `;log runme` 执行 `/mnt/us/RUNME.sh`

## 二进制必须匹配软浮点 ABI

这台设备的用户态是**软浮点（armel）**：`/lib/ld-linux.so.3` 存在，`/lib/ld-linux-armhf.so.3` 不存在。

硬浮点二进制在这台机器上**根本无法执行**——不是功能异常，是 exec 直接失败，而且通常没有任何可见报错。v0.1.0 曾因此打包了硬浮点程序，表现为 `RUNME.sh` 静默无效、`install.log` 从未生成，看起来「装上了但不工作」。

判断依据：

```sh
# 设备上不存在硬浮点加载器，即为软浮点用户态
ls -l /lib/ld-linux-armhf.so.3
# 交叉编译产物应满足 e_flags 含 0x200（EF_ARM_ABI_FLOAT_SOFT）
```

越狱自身的判据与此一致：`jb.sh` 用「`/lib/ld-linux-armhf.so.3` 是否存在」在 `kindlepw2` 与 `kindlehf` 之间选择载荷，日志记作 `J:1:0:0:kindlepw2`。

重建统一走 `./tools/build_kindle_bin.sh`（或 `make kindle-bin`）。该脚本在产物不满足软浮点时报错退出；`tools/package_kindle.py` 打包前还会再校验一次，两道闸都不会让硬浮点混进发布包。

| 二进制 | 链接方式 | 说明 |
|---|---|---|
| `daily-index` | 静态 musl | 息屏随机选取（`random`）与按日期选取，无 libc 版本依赖 |
| `kindlexiping-reader` | 静态 musl | 触控翻句 |
| `screensaver_shield` | 动态 | 必须用设备自带 `libX11.so.6`，按 glibc 2.20 构建，仅要求 GLIBC_2.4/2.12 |
| `fbink_hf` | 动态 | 取自越狱载荷的 `kindlepw2/bin/fbink`，与设备 `/mnt/us/libkh/bin/fbink` 逐字节一致 |

`fbink_hf` 这样取用是有意的：FBInk 完整构建需要 koxtoolchain sysroot，而越狱载荷里那份已经在这台设备上运行，ABI 天然匹配。文件名沿用 `fbink_hf` 只是保持旧路径，内容为软浮点版本。

`screensaver_draw` 已移除：它从未被任何脚本调用（绘图由 `draw.sh` 直接调 fbink 完成），留着只会多一个 ABI 隐患。

## RUNME 采用分发器，不再独占

`/mnt/us/RUNME.sh` 是**共享单槽**：其他 Kindle 项目（USB 联网、hotfix 等）也写这个文件，后装者覆盖前者。v0.1.0 直接覆盖它，既让其他项目入口失效，也让自身在 `exec >>` 指向未创建目录时静默退出。

现在的做法：

- `RUNME.sh` 是分发器，只遍历执行 `extensions/kindlexiping261030/runme.d/*.sh`；
- 启用逻辑在 `runme.d/10-enable.sh`，日志仍写 `install.log`；
- 链回旧 RUNME **默认关闭**。设备上留存的 `RUNME.sh` 往往是 USB 联网引导脚本，它调用 `useUsbForNetwork` 会卸载安装正在写入的 U 盘卷，属危险副作用。确需链回时显式指定：

```sh
KINDLE_RUNME_CHAIN=/mnt/us/RUNME.before-kindlexiping.sh ./tools/install_kindle.sh
```

## 越狱方式

本项目**不重新打包或分发越狱漏洞**，也不建议在未确认机型/固件时升级或重刷。请按官方维护的路线操作：

1. 在 [KindleModding 越狱总入口](https://kindlemodding.org/jailbreaking/) 核对你的机型、固件与当前可用方案。
2. 现代固件通常先完成 hotfix，再安装 KPM / Scriptlet；旧方案 KUAL 已过时。
3. 本项目通过已有 hotfix 的 `;log runme` 入口安装运行时，不依赖 KUAL、MRPI 或 KOReader。
4. 越狱有风险，可能失去保修或导致设备不可用；操作前自行备份书籍与文档。不要把本项目的“安装成功”理解为“越狱一定安全”。

参考：

- [KindleModding jailbreaking](https://kindlemodding.org/jailbreaking/)
- [WinterBreak](https://github.com/KindleModding/WinterBreak)
- [Hotfix](https://github.com/KindleModding/Hotfix)
- 屏保引擎 [kindle-custom-screensaver](https://github.com/chengandre/kindle-custom-screensaver)（MIT）

## 安装步骤

### A. 电脑脚本安装（推荐）

```sh
./tools/install_kindle.sh
```

脚本会：

1. 检查 `/Volumes/Kindle`；
2. 备份现有 `RUNME.sh` 到 `RUNME.before-kindlexiping.sh`（仅首次）；
3. 复制 `extensions/kindlexiping261030/`、`documents/栖息*.sh`；
4. 安装 `RUNME.sh` 分发器（只跑 `runme.d/`，不覆盖其他项目）；
5. 同步文件并提示安全弹出。

### B. 手动安装

解压发布包，把 `extensions/` 和 `documents/` 合并复制到 Kindle 根目录，并用发布包的 `RUNME.sh` 替换根目录同名文件；替换前先把它改名备份。

### C. 在 Kindle 上启用

安全弹出后，在 Kindle 搜索框输入：

```text
;log runme
```

回车后设备会：

- 通过分发器执行 `runme.d/10-enable.sh`；
- 把可执行文件复制到 `/var/tmp/kindlexiping-bin`；
- 启动屏保守护进程；
- 在 `/mnt/us/extensions/kindlexiping261030/install.log` 写入结果，其中会有一行 `device: soft-float (armel)` 或 `device: hard-float (armhf)`。

回到主页，按电源键休眠，锁屏应为当天摘录。若没有变化，先看 `install.log` 是否存在：**该文件不存在就说明 `;log runme` 未曾成功触发**，而不是屏保逻辑出错。

## 日常使用

- **每次息屏换一段**：休眠时随机抽取，并避开上一次所在的书籍块，因此书名与正文一起变化。
- **换上一句 / 下一句**：书库中打开「栖息 · 翻阅」，按屏幕左半/右半切换，底部中间退出。在翻阅页选中的句子只在**下一次**息屏生效一次，之后回到随机轮换。
- **重新启用锁屏**：打开「栖息 · 开启每日锁屏」。
- **恢复原厂锁屏**：打开「栖息 · 关闭并恢复」。
- **重启后**：上游引擎不设置开机自启，需要重新执行 `;log runme`；但若已安装 `emergency.sh`，设备会自己起 SSH，电脑端可以直接 `tools/deploy_over_wifi.sh` 远程完成，不必插拔 USB。
- **完全卸载**：先关闭，再删除 `/mnt/us/extensions/kindlexiping261030/`、`/mnt/us/documents/栖息*.sh`；若 `RUNME.before-kindlexiping.sh` 存在，把它改回 `RUNME.sh`。

## 联网维护（不必每次插 USB）

设备进入 USB 大容量存储模式时，Kindle 会**主动关闭 Wi‑Fi**，所以「插着 USB 同时联网远控」在硬件上不成立；休眠时 Wi‑Fi 也会断。要避免每次部署都插拔数据线，靠的是让设备开机后自己把 SSH 起起来。

`kindle/emergency.sh` 安装到 `/mnt/us/emergency.sh`。hotfix 的 `/etc/upstart/kmc.conf` 在每次 `framework_ready` 时执行它（开机、框架重启、退出 USB 存储模式都算），因此不需要 `;log runme`。它做三件事：

- 等 `wlan0` 拿到地址（最多 3 分钟，避免与 Wi‑Fi 驱动的启动顺序赛跑）；
- 启动 dropbear SSH（2222，密钥登录、禁用密码），失败时退回 telnet（2323）；
- 启动后在后台看护约 10 分钟，掉线自动重连。

脚本一开始就 fork 到后台再立即返回，不会阻塞开机界面。

电脑端配套：

```sh
tools/deploy_over_wifi.sh              # 部署到设备并重启守护进程
tools/deploy_over_wifi.sh --capture    # 另外把唤醒后的屏幕帧拉回本机
KINDLE_HOST=192.168.1.83 tools/deploy_over_wifi.sh
```

前提只有一次：装过 `emergency.sh` 后设备至少开机一次，让 hotfix 执行它。之后设备醒着、没插 USB 时就能直接部署。

通道是否可用看 `/mnt/us/remote-autostart.log`，其中出现 `RESULT: ssh listening on 2222` 即成功。

## 已知限制

- 当前固件 5.16.2.1.1 低于上游屏保引擎声明的 `>= 5.16.3` 起测范围，必须在真机验证后确认；若守护进程无法接管 renderer，关闭脚本仍可恢复原厂行为。
- 带 Special Offers 的广告版 `ad_screensaver` 未在上游完整验证。
- Kindle 原生锁屏层不支持可靠触控；翻句在解锁后的独立页面完成，不伪装成锁屏可点击。
- 原生 reader 的触控坐标由设备 ABS 范围归一化到 1072×1448，若你的机型分辨率不同需重新适配。
- 睡眠期间不保持进程，也不联网；锁屏时间在进入休眠的瞬间写入。
- 联网维护依赖设备处于唤醒且未插 USB 的状态；休眠后 Wi‑Fi 断开属预期，按电源键唤醒即恢复。

## 验收边界

已完成（本机可验证的部分）：

- 4 个二进制均为 ELF32 ARM、软浮点（`e_flags=0x5000200`）；`daily-index`、`kindlexiping-reader`、`xscreen` 为全静态（无 `PT_INTERP`），不依赖设备 glibc 与 libX11；
- `daily-index` 的选取算法与网页端、Python 端一致（同日同序号）；
- `xscreen` 的 X11 协议实现已用最小模拟 X 服务验证：窗口树遍历正确（根窗口与 2 个子窗口各收到一次 `ClearArea`，exposures=1）；面板未变返回 2、面板确实重绘返回 0、连不上 X 返回 3 且不挂起、`selftest` 正确读出 1072×1448；
- 打包脚本会拒绝硬浮点二进制（已实测触发）；
- 10 项单元测试通过，文件已部署到设备的 `extensions/`。

未验证（需要真机唤醒，本机无法代劳）：

- 唤醒后 `xscreen wake` 是否真的让面板脱离海报（需休眠/唤醒一次，再看 `custom_ss.log` 的 `repaint ok` 与 `screen-after-wake.raw`）；
- 翻句页的真实触控响应。

`install.log` 是否出现 `device: soft-float (armel)`，是判断二进制是否被设备接受的第一条证据。
